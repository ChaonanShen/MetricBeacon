---
1. 执行摘要
|要素|内容|
|-|-|
|一句话问题|Prometheus + Grafana 用户在告警排查、临时分析和发布验证时，需要手动查找 Dashboard、编写 PromQL、跨页面拼接图表，分析过程难以保存和复用。|
|一句话方案|在 Grafana 内提供一个自然语言驱动的指标分析工作台：用户通过对话生成 PromQL 和临时图表，多图同屏分析，必要时手动保存到 Dashboard，并结构化保存会话。|
|一句话价值|将“手动找图表、写 PromQL、截图转述”升级为“自然语言生成分析视角、持续追问、可回放可分享”，降低指标分析门槛并沉淀排障经验。|
|全周期成功标准|MS4 交付可内部/对外试用版本：PromQL 一次可用率达到约 70%，核心分析流程稳定可用，会话沉淀和基础 Playbook 复用路径成立。|
|MS1 成功标准|跑通“自然语言输入 → 指标检索 → PromQL 生成与校验 → 临时图表展示 → 会话保存/恢复 → 手动保存到 Dashboard”的最小闭环。|
|核心边界|全周期聚焦 Prometheus metrics；日志/链路只做预留或轻量查看，不做自动 RCA、不做自动修复、不做完整 Dashboard 编辑器、不做多租户/计费系统。|

产品定位：
面向 Prometheus + Grafana 体系的自然语言可观测性指标分析工作台。
它不是 Grafana 的替代品，不是纯聊天机器人，也不是完整 AI SRE。它是嵌入 Grafana 的工作台，帮助用户把排障意图快速转化为可执行 PromQL、可交互图表和可复用分析过程。

2. 背景与问题定义
2.1 当前用户流程
收到告警或需要临时分析
  → 知道 Dashboard 名称：搜索 Dashboard，调整时间范围和变量
  → 知道指标名：进入 Explore，手写或半可视化构造 PromQL
  → 不知道指标名：在 Metrics explorer/browser 中试探搜索
  → 需要多图对比：打开多个 Dashboard / Explore tab
  → 有价值图表：复制 PromQL，手动创建 Panel
  → 排查结束：截图发群、口头转述，或什么都不留
2.2 三个核心痛点
|痛点|表现|本质|
|-|-|-|
|图表查找成本高|用户知道想看什么现象，但不知道指标名、标签名、Dashboard 或 PromQL 写法。|用户意图和 Grafana / Prometheus 资源之间缺少语义映射层。|
|监控面板视角局限|固定 Dashboard 难以覆盖所有排障视角，临时分析需要多次改查询、换维度、开新页面。|Dashboard 是稳定沉淀物，排障需要动态、临时、多图的分析工作台。|
|经验沉淀困难|一次排障中的问题、查询、图表、修改和结论难以完整保存，也难以被下次复用。|仅保存 PromQL 不等于保存经验；需要会话级、结构化的过程记录。|

2.3 目标用户
|用户|典型场景|技能水平|
|-|-|-|
|SRE / 运维工程师|值班告警排查、巡检、复盘|熟悉 Grafana 和 PromQL，但高压场景下希望减少手工操作|
|后端开发工程师|发布后验证、接口异常排查|了解基础指标，不一定熟悉复杂 PromQL 和内部指标命名|
|平台工程师|维护 Grafana、Dashboard、指标体系|熟悉平台能力，需要降低他人使用门槛|
|新加入工程师 / 业务用户|临时查看服务状态或理解监控数据|不熟悉 Dashboard 结构和指标语义|

2.4 JTBD 任务故事

当凌晨被告警叫醒，只知道服务名和异常现象时，我想要立即看到该服务关键指标和异常时间段对比图，以便在 1-2 分钟内判断是否需要升级为事故。

当固定 Dashboard 没有覆盖当前排障视角时，我想要快速生成、调整并并列查看多个临时图表，以便缩小问题范围，而不是反复切换 Dashboard 和 Explore。

当排障完成后，我想要保存完整分析过程并分享给同事，以便复盘时能还原分析路径，类似问题再次出现时能复用。

3. 机会分析
|机会|用户未满足需求|MS1 覆盖方式|
|-|-|-|
|O1 自然语言生成指标图表|不会写或不想写 PromQL，但需要快速看到指标。|Agent 检索指标字典，生成并校验 PromQL，展示临时图表。|
|O2 临时多图分析|排障时需要多指标、多维度、多时间窗口对比。|左对话 + 右多图工作台，默认增量追加临时图表。|
|O3 会话级经验沉淀|查询、图表、修改、结论难以回放和复用。|自动保存结构化会话，支持搜索、分享、Fork。|
|O4 标准分析入口|新手不知道常见排障应该先看什么。|预置 5-8 个分析模板，模板执行后生成普通会话。|
|O5 指标语义增强|内部指标命名、标签含义只有少数人清楚。|基础指标字典：Prometheus Metadata + Dashboard 抽取 + 少量人工补充。|

4. 方案决策
决策 1：产品形态选择 Grafana App Plugin
|备选方案|判断|
|-|-|
|Grafana App Plugin|选择。可复用 Grafana 登录态、权限、数据源、Dashboard API、插件分发和页面导航。|
|独立 Web 应用|不选。需要重做认证、权限、数据源和 Grafana 上下文接入。|
|Panel Plugin|不选。Panel 容器太小，不适合会话列表、多图工作台和分享/Fork。|
|直接改造 Explore|不选。需修改 Grafana core，不符合插件分发和项目边界。|

决策：MS1 使用 Grafana App Plugin + backend component。若会话存储或 AI 代理复杂度超出插件后端能力，可以保留独立后端服务作为后备，但用户入口仍放在 Grafana 内。
决策 2：交互布局选择工作台模式
采用“左侧会话/对话 + 右侧临时图表面板 + 顶部上下文栏”。
Grafana 侧边栏
  └── AI 指标分析工作台
        ├── 左侧：会话列表、当前对话、输入框、模板入口
        ├── 顶部：数据源、时间范围、当前 Dashboard/服务上下文
        └── 右侧：临时图表列表/网格，支持多图对比和轻量编辑
不采用纯聊天窗口，因为排障不是单次问答；也不嵌入某个 Dashboard 页面，避免被已有 Dashboard 结构限制。
决策 3：默认临时图表，用户主动保存到 Dashboard
图表生成后默认作为会话内 Temporary Chart 展示，不自动写入 Dashboard。用户确认图表有长期价值时，点击“保存到 Dashboard”，再确认目标 Dashboard、Folder、标题、PromQL、图表类型和插入位置。

选择理由：
- 排障过程包含大量试错图表，自动写入会污染共享 Dashboard。
- 临时图表降低探索心理负担，保存确认保证正式资产质量。
- Grafana 原生 Dashboard 适合作为沉淀结果，不适合作为每次临时分析的默认容器。
MS1 保存策略：
- 优先支持保存为新 Panel。
- 不覆盖已有 Panel。
- 保存前检查 dashboards:write 权限。
- 保存成功后记录 dashboardUid、panelId、version、savedBy、savedAt。
- 保存失败时保留临时图表，并展示可理解原因。
决策 4：自然语言为主，PromQL/参数编辑为辅
用户主要通过自然语言表达分析需求，例如：
看 checkout 服务过去 30 分钟的错误率。
把错误率按接口拆开。
把刚才那张图时间范围改成过去 6 小时。
同时，生成结果必须可查看、可编辑、可回退。MS1 支持编辑：
- PromQL
- 时间范围
- 图表类型
- 图表标题
- 分组维度
- 基础过滤条件
不做完整 Grafana Panel Editor，不做 Transform、字段覆盖、复杂阈值、Axis、Tooltip、Legend 高级配置。
决策 5：插件后端运行轻量 Agent
前端不直接调用外部 AI API。插件后端负责 Agent 循环、工具调用、AI 请求代理、数据脱敏、权限校验、日志、限流和成本统计。

MS1 Agent 工具控制在少量核心工具内：
|工具|作用|
|-|-|
|search_metrics|检索指标字典，召回候选指标|
|get_metric_labels|获取标签名和值样例|
|generate_promql|基于意图和候选知识生成 PromQL|
|validate_and_execute|校验 PromQL 并执行查询|
|generate_chart|生成图表配置|
|save_to_dashboard|在用户确认后写入 Dashboard|

Agent 可自主搜索指标、生成查询、校验和自我修正；写入 Dashboard 必须用户确认。Agent 不允许删除数据、覆盖 Panel、修改 Grafana 配置或调用未授权外部系统。
决策 6：知识库采用基础指标字典
MS1 不建设完整企业知识库，先做与 PromQL 生成直接相关的基础指标字典。
|字段|来源|用途|
|-|-|-|
|指标名、类型、Help/Description|Prometheus Metadata|确保指标真实存在，辅助语义匹配|
|标签名、标签值样例|Prometheus labels/label values|构造过滤条件和分组维度|
|Dashboard / Panel 查询样例|Grafana Dashboard 抽取|学习团队已有成熟查询模式|
|关键指标业务说明|少量人工补充|弥补原始 metadata 缺少业务语义的问题|

不做复杂知识图谱，不深度读取代码仓库，不接入所有业务文档，不让 AI 无限制访问内部知识。
决策 7：MS1 沉淀完整会话，不自动生成 Playbook
经验沉淀采用：
完整会话回放 + 预置分析模板 + 结构化数据预留
MS1 不自动提炼参数化 Playbook，不自动执行决策逻辑，不做完整事故管理。原因是高质量 Playbook 需要真实会话样本、有效性校验和人工 review，过早承诺会导致范围失控。

5.3 全周期明确不做
|不做事项|理由|
|-|-|
|自动修复或执行变更|高风险操作，不符合人机协作边界。|
|完整 Dashboard 自动生成|对 AI 规划能力和布局质量要求过高，先做好单图/多图工作台。|
|完整 Grafana Panel Editor|会把工作台变成编辑器，偏离临时分析闭环。|
|自动写入或覆盖 Dashboard|容易污染共享资产，必须用户确认。|
|带复杂判断逻辑的专家 Playbook|需要大量专家样本、版本治理和有效性校验，全周期不承诺。|
|日志/链路深度分析|全周期聚焦 Prometheus metrics，Loki/Tempo 只预留扩展或轻量查看。|
|多人实时协作编辑|一致性和权限复杂，分享 + Fork 足够验证协作价值。|
|多租户、计费、License|初期内部验证，后续商业化再设计。|

6. 用户流程
6.1 主流程
flowchart TD
    A[用户进入 Grafana] --> B[打开 AI 指标分析工作台]
    B --> C{入口}
    C -->|自由输入| D[输入自然语言分析需求]
    C -->|模板| E[选择模板并填写参数]
    D --> F[Agent 检索指标字典和上下文]
    E --> F
    F --> G[生成 PromQL 和图表配置]
    G --> H[校验并执行查询]
    H -->|通过| I[右侧展示临时图表]
    H -->|失败| J[自动修正或进入兜底]
    J --> I
    I --> K{用户下一步}
    K -->|继续追问| D
    K -->|编辑图表| L[NL 或手动编辑]
    L --> H
    K -->|保存 Dashboard| M[确认目标和写入内容]
    M --> N[写入 Dashboard]
    K -->|分享| O[生成链接]
    O --> P[接收者只读查看或 Fork]
6.2 异常与边界流程
|场景|用户看到什么|系统做什么|恢复方式|
|-|-|-|-|
|意图不明确|追问或候选指标列表|不直接执行高不确定查询|用户补充服务、指标、维度或选择候选|
|PromQL 语法错误|错误高亮和修正建议|Agent 自动修正一次|用户手动编辑或重新输入|
|指标/标签不存在|相近候选和失败原因|记录失败类型|选择候选或修改条件|
|查询成功但无数据|提示无数据，建议放宽时间/标签|保留原查询和执行状态|调整时间范围或过滤条件|
|查询超时|超时提示和重试入口|降级或限制查询范围|重试、缩小范围或手动编辑|
|AI API 不可用|“AI 暂不可用，已切换手动模式”|保留已有图表和 PromQL 编辑|手动查询或稍后重试|
|Dashboard 保存无权限|权限说明|不写入 Dashboard|用户申请权限或仅保留临时图|
|Dashboard 版本冲突|冲突提示|不覆盖远端变更|重新加载目标 Dashboard 后再保存|

7. 信息架构与数据结构
7.1 核心概念
|概念|定义|
|-|-|
|AnalysisSession|一次完整分析过程，包含对话、图表、PromQL、执行结果、用户操作和备注。|
|Temporary Chart|工作台右侧展示的临时图表，随会话保存，不默认写入 Dashboard。|
|Chart Revision|图表从 AI 生成到用户编辑、最终采纳之间的版本记录。|
|Template|团队预置的标准分析入口，包含参数、步骤和默认图表定义。|
|Fork|基于他人分享会话创建独立副本，继续分析但不影响原会话。|
|Candidate Playbook|MS2 以后从高价值会话中提炼出的候选流程，MS1 仅预留。|

7.2 结构化对象
|对象|字段示例|作用|
|-|-|-|
|AnalysisSession|id, title, owner, visibility, tags, sourceTemplateId, createdAt, updatedAt, dataSourceUid, timeRange|一次完整分析过程|
|SessionTurn|role, content, createdAt, relatedChartIds, summary|关联对话和图表|
|ChartDraft / ChartSnapshot|id, title, query, vizType, timeRange, layout, status, dataSourceUid|临时图表状态|
|QueryRevision|chartId, generatedQuery, editedQuery, finalQuery, editSource|保留 AI 与用户修改差异|
|ChartExecution / ExecutionSummary|chartId, status, errorType, seriesCount, durationMs, sampleRange|查询执行结果和质量判断|
|SessionNote|author, content, relatedTurnId, createdAt|用户结论和备注|
|DashboardSaveIntent|chartId, targetDashboardUid, folderUid, panelTitle, message|写入前确认对象|
|DashboardSaveResult|dashboardUid, panelId, version, savedBy, savedAt|写入结果留痕|
|Template|id, title, scenario, parameters, steps, defaultCharts, owner, version|预置分析模板|
|TemplateRun|templateId, sessionId, params, success, modifiedSteps|验证模板有效性|

关键要求：
- 临时图表和 Dashboard Panel 必须分离。
- 会话记录既要可回放，也要可被机器分析。
- AI 原始版本、用户编辑版本、最终保存版本都要留痕。
- 模板和会话分离：模板是入口，会话是执行结果。
- Playbook 和模板分离：Playbook 是经过真实样本验证后的可复用流程。

9. AI 体验设计
9.1 信号与意图
|要素|内容|
|-|-|
|用户输入信号|自然语言文本、模板参数、当前时间范围、数据源、已生成图表|
|系统识别意图|查询指标、创建图表、编辑图表、解释图表、保存到 Dashboard、分享/Fork|
|置信度来源|模型判断、指标字典匹配、PromQL 语法校验、指标/标签存在性、查询结果状态、历史用户反馈|

9.2 置信度策略
|置信度|策略|
|-|-|
|高|直接执行查询并展示临时图表，同时提供 PromQL 和生成依据。|
|中|展示候选指标或候选 PromQL，用户选择后执行。|
|低|不执行，主动追问服务、时间范围、指标类别或分组维度。|

写操作即使高置信也必须用户确认。只读查询可以高置信自动执行。
9.3 失败兜底
Agent 生成 PromQL 后进行校验：
1. 语法是否正确。
2. 指标是否存在。
3. 标签名是否合法。
4. 查询是否返回数据。
5. 查询耗时是否可接受。
6. 返回数据是否适合当前图表类型。
失败时先自动修正一次；仍失败时展示失败原因、候选指标、可修改方向，并保留 PromQL 编辑框。兜底原则是：用户始终可以通过手动 PromQL 和参数编辑继续前进。
9.4 数据安全与出域边界
所有外部 AI 调用必须经过插件后端代理。
|数据类型|策略|
|-|-|
|用户自然语言问题、PromQL 片段、指标名、指标类型、标签名、图表类型、时间范围|可发送|
|标签值、Dashboard 标题、Panel 标题、服务名、环境名、集群名、会话业务描述、错误信息摘要|脱敏后发送|
|原始指标查询结果明细、大量时间序列数据点、用户身份、API Key、Token、内部访问地址、完整日志、完整 Trace|默认不发送|

若业务安全要求禁止外部 AI，则切换到私有模型或内部 AI 服务方案。

8. 用户可 Fork 该会话，并将服务名替换为 cart、时间范围替换为过去 1 小时。

13. 风险与应对
|风险|表现|应对|
|-|-|-|
|NL→PromQL 准确率不足|生成不存在指标或错误标签|强制接入指标字典；低置信展示候选；保留 PromQL 编辑|
|App Plugin 流式能力不稳定|AI 回复体验差|MS1 先支持非流式；流式作为增强|
|会话持久化方案不清|关闭页面后图表丢失|Spike 明确 Grafana DB/外部 DB/独立服务方案|
|Dashboard 写入污染共享资产|错图被保存|默认临时；保存前确认；记录版本和操作人|
|权限处理复杂|Viewer 能看图但不能保存|临时图表权限与 Dashboard 写权限分离|
|只存聊天文本|后续无法参数化|MS1 强制结构化保存 PromQL、metric、label、图表配置、执行结果|
|自动保存过多导致历史难找|形成新的信息垃圾堆|标题、标签、收藏、搜索、模板来源筛选|
|AI 摘要错误|错误经验被沉淀|摘要默认草稿，用户确认后才作为结论|
|多轮指代错误|修改了错误图|图表编号和标题；匹配多个时必须澄清|
|Playbook 过早复杂化|阶段范围失控|只预留数据结构，不做自动 Playbook|
